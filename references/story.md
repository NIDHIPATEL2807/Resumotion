# Story — Claude Reference

Read this before writing script.md. The screenplay is the most important thing you write — it determines the entire reel.

---

## The one job: find the hero story

Every good reel has one clear through-line. Before listing scenes, answer:

1. **What is the single most impressive thing this person has done?** → This becomes the hero scene (case study / boss level / deal print / blueprint hero drawing).
2. **What do they want to be known for?** → This becomes the thesis.
3. **Who is watching this reel?** → This determines tone and what to lead with.

If you can't answer all three from the resume, you haven't read it carefully enough.

---

## Scene order (default)

```
Open          → set the visual world, hint at what's coming
Name          → who they are
Thesis        → what they stand for / their core approach
Hero story    → the best experience, told as problem → insight → solution → result
Projects      → 2–3 other things they've built (shorter than the hero)
Wins          → awards, competitions, recognition
Skills        → tools and stack
Silence       → one beat of breath
Outro         → CTA, contact, end card
```

Vary the order when the content demands it. A designer might lead with a project visual. A finance person might open on the deal. Follow the story, not the template.

---

## The hero story (most important scene)

This is the scene people remember. It must have:

- **The real problem** — what was broken, slow, manual, or missing? Be specific. Not "improved efficiency" — "C4 diagrams drawn by hand, hours per architect."
- **The insight** — what did they notice that others didn't? Or what approach did they take?
- **What they built** — the actual thing. Steps, stages, or a pipeline if there is one.
- **The result** — a real number if the resume has one. A qualitative win if not. Never invent.

If the resume has no clear problem → solution story, use `experience` format (role + company + one honest line about the work).

---

## Length rules

| Resume richness | Target length | What to include |
|---|---|---|
| Thin: name + role + 1–2 projects, no wins | ~30 s | Opener, name, thesis, 1–2 projects, outro |
| Standard: 2–3 projects, some wins | ~40 s | Full structure, 1 hero, 1–2 projects, wins |
| Rich: 4+ projects, strong case study, many wins | ~50 s | Full structure, hero, 2–3 projects, wins, stack |

Never pad to hit a target. An honest 35-second reel is better than a padded 50-second one.

---

## Copy rules (how to write on-screen text)

- **Verbs over adjectives.** "finds the problem first" not "highly analytical".
- **Numbers when real.** "82% faster" not "significantly faster". If no number exists, use a qualitative win.
- **Short.** ≤6 words per beat group in `punchy` mode. If the user asked for `detailed`, up to ~12.
- **Their words first.** If the resume has a line that's already good, use it. Don't rewrite what's working.
- **The thesis is earned.** The 3 cycling words (see / think / ship, etc.) must connect to actual projects in the reel. Don't write "scale" if there's no evidence of scale.
- **The outro CTA is specific.** "Let's build something." works. "Available for ML roles at Series A–C startups." is better if you have the information.

---

## What to skip

- Projects with no detail in the resume → skip or note as one line only
- Wins with no specifics (just "Finalist") → skip unless user confirms details
- Stack items the person clearly just listed as buzzwords (no project uses them) → omit
- Anything confidential that the user said not to include
- Never add a scene just to fill time

```
               Stages: [stage 1] → [stage 2] → [stage 3]

```

Show every scene. Show every word of on-screen text. The user can't approve what they can't read.
